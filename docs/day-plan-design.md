# 行程篮「多天排期 + 住宿推荐 + 行程单导出」设计方案

> 目标：让用户在行程篮里**手动把已加入的路线划到第 N 天**，系统据此**自动推荐每晚住宿**，最后**导出一份可打印/可存档的行程单**。
> 状态：**待确认** —— 本文 + `docs/day-plan-mockup.html`（可点交互样例）一起给你过目，确认后再编码。

---

## 0. 先看这里：三条硬约束（决定了方案怎么选）

摸了一遍仓库，有三件事会直接约束技术选型，先摊开说：

| # | 现状 | 对方案的影响 |
|---|---|---|
| **①** | **住宿数据是全空的**。`Hotel` 类型、后台录入 UI、详情页展示、地图标记全都就位，但 `seed.ts` 里 27 条路线一律 `hotels: []`，全仓没有任何住宿 JSON | 「自动匹配住宿」**不能只做酒店级推荐**（没数据可推）。必须先做**区域级推荐**（住哪个城镇，附推荐理由），用户/后台补录酒店后自动升级为酒店级候选清单 |
| **②** | **已有一条「区域级住宿建议」数据源**：`src/lib/tripPlans.ts` 每条路线已有 `stay`（前夜住哪）/ `stayReturn`（走完住哪），例：`'성산（城山） 或 제주시（济州市）'` | 这不是可筛选的结构化数据，但**正好能当推荐引擎的知识底座**，零新增数据就能跑通第一阶段 |
| **③** | **零拖拽库、零导出库**（依赖只有 echarts/leaflet/react/react-dom/react-router-dom 五个）；`Hotel` 挂在 `Route` 下、**没有自己的区域字段** | 拖拽用原生 Pointer Events 自研（~150 行）不引三方依赖；导出走**浏览器打印 → PDF**（`@media print`），零依赖；住宿的「区域」由「离它最近的路线」继承推导 |

还有一个同名陷阱，编码时要当心：`src/lib/tripPlans.ts` 名字像行程篮，其实是**详情页的行程建议文案表**，和行程篮无关。行程篮的代码标识符是 `plan` / `plans`。

## 3. 数据模型改动（具体到字段）

```ts
// src/types.ts —— 只加字段，不改语义，旧数据天然兼容
export interface PlanItem {
  routeId: string
  done?: boolean
  /** 第几天（1-based）。undefined = 未分配，落在「待安排」区 */
  day?: number
  /** 同一天内的行走顺序，从小到大。缺省按 items 原顺序 */
  order?: number
  /** 用户锁定的住宿 id（来自某条 Route.hotels），锁定后推荐不再覆盖 */
  stayId?: string
  /** 用户对这晚住宿的备注（"订了海景房，取消需提前 3 天"） */
  stayNote?: string
}

export interface Plan {
  id: string
  name: string
  targetKm: number
  items: PlanItem[]
  /** 出发日期 'YYYY-MM-DD'，填了才在行程单上显示「10/3 周五」 */
  startDate?: string
  /** 每天的用户备注，key 为 day */
  dayNotes?: Record<number, string>
  createdAt: number
  updatedAt: number
}
```

**为什么不新建 `days: PlanDay[]` 数组？** —— `day` 放在 item 上有三个好处：① 旧 `Plan` 不用结构迁移，只 `normalizePlan` 兜底；② 清空某天不会留下空洞的天号；③ 现有「每条路线只算一次」的去重逻辑（`items.some(i => i.routeId === x)`）完全不用动。

**运行时派生，不落库**（`src/lib/dayPlan.ts`）：

```ts
export interface DayPlan {
  day: number
  dateLabel?: string        // 「10/3 周五」，有 startDate 才算
  dateISO?: string
  routeIds: string[]
  distanceKm: number
  gainM: number
  hoursMin: number          // 估算纯步行时长（不含休息）
  difficultyMax: 1 | 2 | 3 | 4 | 5
  /** 与前一天的接力缺口 km（首日为 0 / 未知则 undefined） */
  transferGapKm?: number
  warnings: DayWarning[]
  stay: StaySuggestion | null   // 最后一天为 null（返程日）
}
```

## 4. 交互设计

### 4.1 视图（**已按用户意见定稿：地图不是 Tab**）

- **页签只有两个**：「清单」（默认）/「按天」。
- **「行程位置」地图保持常驻**，位置与改造前完全一致（在汇总卡之后、**不受页签切换影响**）。
  理由：地图是行程篮一直在用的参照物，收进 Tab 会让人每次都要多点一下才能看分布。
- 顶部新增控件：**出发日期**（`input[type=date]`，可选）→ 填了之后 Day 卡片自动显示星期、行程单带日期。

### 4.2 手动划分天数：三种操作并存

| 操作 | 适用 | 实现 |
|---|---|---|
| **拖拽**（渐进增强） | 桌面整理大量路线 | **原生 HTML5 Drag and Drop**（`draggable` + `onDrop`），零依赖，约 30 行 |
| **卡片上的「第 N 天」下拉** | **手机 / 无障碍（主路径）** | `<select>`，选项 = 待安排 + Day1…DayN |
| **↑ ↓ 按钮** | 同一天里调顺序 | 直接交换 `items` 数组里相邻同天元素 |

> **决策 D1 已落地**：最终没引 dnd-kit，也没自研 Pointer Events 手势 ——
> 原生 HTML5 DnD 在桌面够用，移动端由「下拉选天」兜住（原生 DnD 在触屏上不触发，
> 所以下拉**必须**是主路径而不是备选）。这样拖拽就算在某种设备上失效，功能也不受影响。
>
> ⚠️ **「同一天里的顺序」没有单独的 `order` 字段**：它就是 `items` 数组的先后顺序。
> 多一个字段就等于多一份真相，「按加入顺序」和「第 N 天的第几条」会对不上。

### 4.3 Day 卡片长什么样


## 5. 每天的计算与校验规则

**耗时估算**（写在 `dayPlan.ts`，口径要显式标注）：
```
hours = distanceKm / 3.6 + gainM / 450     // 平地 3.6km/h + 爬升补偿
```
> 这是估算， UI 上标注「估算值，实际按官方建议耗时为准」；详情页已有官方耗时口径的地方不覆盖。

| 校验 | 触发条件 | 表现 |
|---|---|---|
| **R1 超载** | 单日 > 20 km 或 > 6.5 h | 卡片橙色描边 + 「这天偏重，建议拆成两天」 |
| **R2 过轻** | 单日 < 5 km 且不是首尾日 | 灰色提示「可以再塞一条短线」 |
| **R3 接力断口** | 前一日终点 ↔ 当日起点直线距离 > 1 km | **必报**：写明「需接驳约 X km，查一下公交」。这个不能省——偶来路线并非首尾全部相连，例如 06 终点「偶来旅客中心」到 08 起点「月坪」之间要坐车 |
| **R4 跨海的做法要看船班** | 当日含「离岛」标签（01-1 牛岛 / 10-1 加波岛 / 18-1·18-2 楮子岛） | 提示「需坐船，末班船务必确认；错过得住岛上」，并让当晚住宿**强制**推荐岛内 |
| **R5 末日** | 最后一天 | 不推荐住宿，显示「当日返程」 |

## 6. 住宿推荐引擎（`src/lib/stayMatch.ts`）

### 6.1 两级输出

| 级别 | 输出 | 数据来源 | 什么时候有 |
|---|---|---|---|
| **L1 区域级**（保底） | 「建议住城山」+ 一句理由 | `tripPlans[code].stayReturn` / `.stay` | **立刻就有**，零数据依赖 |
| **L2 酒店级**（增强） | 带距离/价格/评分的候选清单 | `Route.hotels`（用户后台录入） | 用户补录后自动出现 → **叠加在 L1 之上**，不覆盖 |

### 6.2 推荐规则（按优先级，命中即止）

| 序 | 规则 | 理由 |
|---|---|---|
| 1 | 用户已 `stayId` 锁定 → 原样展示，不再推荐 | 用户的手动选择优先级最高 |
| 2 | 当天含离岛标签 → 推荐该岛（`tripPlans`.stayReturn），且**只在岛内候选里找** | 错过末班船得住岛上 |
| 3 | 取当天**最后一条路线**的 `stayReturn` 作为首选区域 | 走完就住下来最合理 |
| 4 | 存在第 N+1 天 → 取其**第一条路线**的 `stay` 做交叉校验；两值不一致时同时展示两区域并提示取舍 | 「今晚住终点附近」和「明早好出发」常常冲突，要显式告诉用户 |
| 5 | 候选打分排序（见下） | 把离当晚终点、明早起点都近的排前面 |
| 6 | 全无数据 → 降级为 L1 区域文本 + 「去素材管理补录住宿」深链，**不编造任何酒店名** | 遵守项目「不编造」纪律 |

### 6.3 候选打分

```
每晚候选 = 全部路线 hotels 去重后，筛出「距当晚终点 8km 内」的部分
每晚上分 = 0.6 × dist(当晚终点) + 0.4 × dist(明早起点)     // km，越小越靠前
前夜候选 = 筛出「距第一天出发点 8km 内」的部分，只按 dist(出发点) 排序

tie-break：两者都一样 —— 有 rating 的按 rating 降序，再按 priceRange 升序
```

> ⚠️ **最后一天同样要给住宿建议**（用户明确要求）。走完最后一段当晚仍要落脚，
> 多半第二天才坐飞机 / 船返程 —— 「末日不推荐住宿」这条规则已经从 `stayMatch` 里删掉了。
> 另外**出发前一晚单独一档**（见 §6.5），它不属于任何一天，权重也完全相反（离出发点近优先）。
距离用 Haversine 直线距离（`src/lib/geo.ts` 里已有相关工具可复用）。

> **决策点 D2**：现在零住宿数据，你是想 ①我先在后台批量补一批真实住宿（我做，需要你确认区域范围）；②留空位给你自己录；③干脆第一阶段只出 L1 区域级推荐。**我推荐 ③ + ① 并行**：先把引擎和 UI 做通拿放到一边，数据由你决定什么时候填，填了自动升级。

### 6.4 「为什么推荐这里」必须写出来

每个住宿建议卡都要有一行理由（引擎自动生成，不是写死的文案），例：
- `今天终点「温坪」距住宿 0.8km，明早出发点就在附近`
- `偶来 03 官方行程建议：走完当天入住 표선（表善）`
- `备选区域「제주시（济州市）」：离今晚终点近，但明早去「表善」需约 40 分钟车程`

让用户能判断要不要听推荐的。

## 8. 兼容迁移

### 8.1 旧行程篮（无 `day` 字段）→ **不做迁移**
用户明确：**不用兼容之前的行程篮版本。**

- `normalizePlan` 只做原本那件事（补 `items` 数组），**不新增任何字段兜底**。
- 备份文件 `version` 固定写 2，导入时**不识别 version、不做升级转换**：缺字段就是缺字段。
- 结果：老行程篮里的路线全部**落在「待安排」**，由用户自己排一次。
  这比写一个「按加入顺序自动平均分配」的迁移要好 —— 自动排出来的顺序十有八九不是他想要的，
  而手动排的成本只有几次拖拽。

### 8.2 备份文件写作 v2
```ts
export type BackupFile = {
  version: 2                  // 只是写入端的标记，导入时不识别
  exportedAt: number
  routes: Route[]
  plans: Plan[]               // v2 起含 day / stayId / startDate / dayNotes
  settings?: AppSettings
}
```
老备份**能读进来但不会升级**：`plans` 里没有 `day` 字段就是没分天，落到「待安排」，
用户重排即可。**刻意不做「半吊子复活」式的兼容转换** —— 结构一变还要假装无缝，
最容易算出一个错的行程单。

### 8.3 `useActivePlan` 新增 API
```ts
assignDay(routeId, day | undefined)   // 含「移回待安排」
moveInDay(routeId, dir: -1 | 1)       // 同天内上下移
setStartDate(iso | undefined)
setDayNote(day, text)
lockStay(day, hotelId | undefined)    // 存到「当天最后一条」PlanItem.stayId
```

## 9. 可选项（**不做也不影响主线**，别当必做清单看）

| 可选项 | 收益 | 代价 | 建议 |
|---|---|---|---|
| **O1 图片长图导出** | 朋友圈/群聊分享更好看 | +1 依赖（html-to-image ~40KB），中文字体 & 跨域图片易踩坑 | 二期再说，先把 PDF 做好 |
| **O2 按里程自动排天** | 一键「按每天 15km 帮我分好」 | 贪心算法简单，但要处理「必须坚持流程 → Label 路线顺序不能被拆到不同天」之类的约束 | 手动为主的话优先级不高；确实实用的话可加，放在独立按钮，不进默认流程 |
| **O3 分享链接**（plan 状态编进 URL） | 发给同伴直接打开 | 27 条路线还好，路线多了 URL 会很长 | 你有「发给旅伴」的需求再说 |
