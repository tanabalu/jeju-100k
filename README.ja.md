# 済州オルレ・100km ガイド（済州島 Jeju Olle Trail）

> 🌐 言語 / Language： [中文](README.md) · [English](README.en.md) · **日本語** · [한국어](README.ko.md)
>
> 📌 データ取得の経緯、試行錯誤の記録、過去のデータスナップショットは **[CHANGELOG.md](CHANGELOG.md)**（中国語）に移しました。本ドキュメントは現状の使い方のみを扱います。

## 概要

済州島の 29 本のオルレ（올레길）を自分の行程にまとめ、距離を自動計算して 100km を達成できるか確認したり、出発点・到着点、沿道の宿泊施設、景色、アルバムを管理したりできます。

純フロントエンド。データはローカルブラウザ（localStorage + IndexedDB）に保存されます。依存関係は npm で管理し、エンドユーザーは `npm run build` が出力する静的サイトを使います。

## クイックスタート（概要）

| 手順 | コマンド | 説明 |
| --- | --- | --- |
| 1 | `npm install` | 依存関係をインストール |
| 2 | `npm run dev` | ローカル開発、http://127.0.0.1:5180 を開く |
| 3 | `npm run build` | エンドユーザーが使う静的サイト `dist/` を出力 |
| 4 | `npm run preview` | ビルド成果をローカルで検証 |
| 5 | デプロイ（任意） | `dist/` を任意の静的サーバー / Dokploy サブパスに配置 |

> 要点：**地図背景データは OpenStreetMap 由来で、世界中カバーされ、API キー不要**。済州の街路・海岸線・地形は正常に表示されます。オフライン時は地図エリアが空になりますが、距離計算などのコア機能には影響しません。§5 参照。

## 1. あらかじめ登録されるもの

初回起動時に、公式の **29 本のオルレ**（出典：jejuolle.org と公式 Olle アプリ）が自動的に書き込まれます：

- **本線 21 本 + 支線 6 本**（1-1 牛島、7-1、10-1 加波島、14-1、18-1 上楸子、18-2 下楸子）
- **3 号線と 15 号線には A/B の別走路が 1 本ずつ追加**（`03-A`/`03-B`、`15-A`/`15-B`、下記参照）
- 公式距離は「実際の距離」に格納済みなので、**距離は公式値を優先**、直線推定はしません
- 公式難易度 Low / Medium / High は 2 / 3 / 4 つ星にマッピング済み
- 本線は 1 本 10.1～20.9 km。29 本の合計は **430 km**（`OLLE_TOTAL_KM` は `SPECS` から導出、ハードコードなし — ホームの「437km 27코스」は宣伝上の数値。どちらも正しく、どちらかに合わせて書き換えないこと）
  — A/B は同じ区間の二者択一なので、合計はその区間を二重に数えています（+27.6 km）。各番号を 1 回だけ数える目標は 403 に。

| データ | 現状 |
| --- | --- |
| 路線番号、出発/到着名称、公式距離、公式難易度 | 公式サイト（jejuolle.org）、そのまま利用可 |
| ルートの幾何（形状、出発/到着の緯度経度） | **29 コースすべてに軌跡**（28 は実測 + `15-B` は OSM 路網からの推定）——下記参照 |
| 標高と累積獲得標高 | 軌跡から算出、または軌跡沿いに補完サンプリング、下記参照。**29 コースすべてに標高データあり** |
| 沿道の宿泊 | OSM から取得した 239 件を事前登録（12コースが該当）、`/admin` で編集可 |
| カード表紙 | 該当ルート周辺の風景写真（Wikimedia Commons 自由ライセンス、要 `scripts/fetch_photos.py`）。未実行なら公式ルートマップにフォールバック |
| 見どころ、アルバム | 空で事前登録、`/admin` で入力 |

### 獲得標高の計算方法（重要）

事前登録 29 ルートはすべて実軌跡を持ちます（`public/tracks.json`、実行時に `fetch` で読み込み、**localStorage には保存しません** — ファイルを差し替えればトレースが変わる）。`src/lib/olleeElevation.ts` の標高列は `scripts/build_elevation_from_tracks.py` が**その同じ軌跡点から派生**したものなので、seed データと実行時の重ね合わせが完全に一致し、プロファイルが「近似→実測」へ飛ぶことはありません。

- 4 コース（`09 / 14-1 / 18-1 / 18-2`）は軌跡が標高を持ち，其余 25 コースは SRTM 30m を軌跡沿いに補完サンプリング
- 獲得標高は隣接点差に **3m ヒステリシス閾値**を適用し、地形データ自体の揺らぎを抑えます
- 29 コースの合計は **6504 m**

⚠️ 補完した標高も **推定値であり、公式の実測獲得標高ではありません**：SRTM 30m の分解能は約 30m なので、海岸の小さな段差は 平坦化されます。プロファイルの形や「どちらがきついか」の順位付けには使えますが、ペース配分や補給計画では目安として扱ってください。

このデータを更新するには：

```bash
python3 scripts/fill_track_elevation.py         # tracks.json 内の標高欠損軌跡を補完（キャッシュあり、新点のみ）
python3 scripts/build_elevation_from_tracks.py  # tracks.json から seed 用の標高列を再生成
```

自分で作ったルートにはサンプリングデータがなく、`/admin` の「経由点」で各点に標高を入力します；**標高を持つ点が 2 未満の場合、獲得標高は 0 ではなく「—」と表示**（0 だと平坦だと誤解させるため）。

### 3 号線と 15 号線の A（山線）/ B（海線）

公式はこの 2 つの番号を **A = 山線** と **B = 海線** に分けています。出発点・到着点は同じで二者択一、
どちらかを歩けばその番号を歩いたことになります：

| コース | 走路 | 距離 | 所要 | 難易度 | 走向 |
| --- | --- | --- | --- | --- | --- |
| `03-A` | 山線 | 20.9 km | 6~7h | ★★★★ | 内陸の中山間帯、桶岳・独子峰経由 |
| `03-B` | 海線 | 14.6 km | 4~5h | ★★ | 海岸（바당올레）。신풍신천바다목장 で A 線に合流。**実測軌跡あり 14.75 km** |
| `15-A` | 山線 | 15.5 km | 5~6h | ★★★ | 山林道、錦山公園・納邑林道・과오름 経由 |
| `15-B` | 海線 | 13.0 km | 4~5h | ★★ | 海岸：翰林港 → 郭支 → 漢潭海辺散歩路 → 涯月 → 高内浦口 |

コース一覧・行程かごでは**それぞれ独立した 1 本**として扱われます（バッジに `-A` / `-B`、カードタグに
「山線」/「海線」。この 2 語で検索して絞り込みもできます）。

### 実軌跡と座標精度（2026-10-03 時点）

**29 コースすべてに軌跡があります**（`public/tracks.json`。実行時に `fetch` で読み込み、**localStorage には入りません**。差し替えるときはファイルを置き換えるだけ）。**28 本は実測**で、海線 `15-B` のみ** OSM の歩道路網からの推定**です（後述）。自分で作成したコースは、従来どおり起終点をつないだ破線の近似で、獲得標高は「—」表示です。

`03-B` の軌跡は 2026-10-03 に補完しました：OSM の `올레길3` 親リレーションは `올레길3A` / `올레길3B` という子リレーションを持ち、両者は** way を一切共有しません**（`A∩B=0`）。親自身が持つ 32 本の way が両線共通の首尾区間です。したがって「親の 32 本 + 3B の 25 本」を縫い合わせれば 14.88 km の連続した海線になります（公式 14.6 km、覆率 1.02）。独立したコミュニティ KML（`Jeju Olle 3B`、14.84 km）も首末点が一致し、2 つの情報源が符合します。

`15-B` は実測軌跡が入手できませんでした。OSM には 15 番線の **route リレーションが存在せず**（島全体の 22 個の 올레 リレーションに含まれない）、公式ページ `jejuolle.org/trail#/road/15_B` は**ラスタ版の路线図のみ**です（`assets/Road-*.js` は `road_15-B_map_pc.jpg` を参照しているだけでベクター座標なし）。コミュニティサイトの `JejuOlle15a/15b` も両方 404 です。そこで**路網から推定**しました：翰林港〜高内浦口間の歩ける OSM way と海岸線を取り出し、「**海岸に沿う最短路**」のコスト（区間長 × 道路種別係数 × 海岸からの距離ペナルティ）で Dijkstra を実行し、連続した **12.26 km / 獲得標高 45 m** の走向を得ました（公式 13.0 km、覆率 0.955）。走向の妥当性を示す根拠：公式が挙げる 4 つの地点 — 運龍岬無人道灯、濟州海水浴場海女學校、金城里海、곽지海水浴場 — が**すべて軌跡の 80 m 以内**に入ります。また獲得標高 45 m は公式の「全线平坦、无台阶、难度低」という説明と一致します。実測ではなく推定であり、公式距離より 5.7% 短いため、行程を組む際は公式値を優先してください。
軌跡のあるコースは地図上で**実線**（白フチ + 緑の芯）で描かれ、出発・到着点は軌跡の両端に吸着し、獲得標高は軌跡に沿って地点ごとに累積します。

| 項目 | 現状 |
| --- | --- |
| 軌跡の出所 | OSM の route relation / OSM の単独 way / 全区間の Olle GPX をコース番号ごとに**比較選定**（`tracks/osm/*.geojson`） |
| 公式 ↔ 軌跡の差 | 16コースが ±5% 以内。**13コースが超過**、うち `15`（+19.0%）と `08`（−11.9%）は ⛔ 判定 |
| 標高の出所 | 4 コース（`09 / 14-1 / 18-1 / 18-2`）は軌跡が持つ標高を利用。残り 25 コースは軌跡に標高が無く、SRTM 30m を軌跡沿いに補完サンプリング。**29 コースすべてに標高あり** |
| 獲得標高の合計 | 29 コースすべてにデータあり、計 **6504 m** |

⚠️ **二手データであることの限界**：これらは OSM / GPX から取得したもので、**公式のルート変更には自動で追従しません**。
画面の「距離」は常に `SPECS` の公式値を取り、詳細ページで「軌跡実測 X km」を併記するので、上の表の差がページ上の数字の矛盾になることはありません。
ただし `15` / `08` の**獲得標高と地図上の形状**は割り引いて見てください。

> 📌 3ソースの比較方法、コースごとに採用・却下した幾何、各ラウンドの偏差スナップショットは [CHANGELOG.md](CHANGELOG.md)（中国語）にあります。

### 標高と獲得標高の計算方法

優先順位：**手入力の「実際の累積獲得標高」** > **軌跡が持つ標高**（`elevSource: track`）> **軌跡沿いの補完サンプリング**（SRTM 30m）
> **経由点の手入力標高** > どれも無ければ「—」。

- 標高列は `public/tracks.json` の軌跡点そのものです（`src/lib/olleeElevation.ts` はそこから派生）。
- 累積は**3m のヒステリシス閾値**付きの隣接差分で、地形データ自体のノイズを抑えます。
- **標高を持つ点が 2 つ未満なら 0 ではなく「—」**（0 だと「ずっと平坦」と誤認される）—— 軌跡が無い自前のルートでのみ発生。

データを更新する：

```bash
python3 scripts/check_official_consistency.py            # 公式 ↔ 実幾何を1件ずつ照合（変更後は必ず実行）
python3 scripts/fill_track_elevation.py                  # tracks.json 内の標高欠損軌跡を補完（キャッシュあり、新点のみ）
python3 scripts/build_elevation_from_tracks.py           # tracks.json から seed 用の標高列を再生成
```

### 軌跡の再取り込み / 追加

スクリプトのロジックを変更したら先に回帰テスト（いずれもオフライン）：

```bash
python3 scripts/selftest_fetch_osm.py        # 縫合と判定
python3 scripts/selftest_import_tracks.py    # 取り込みと向き補正
```

本番：

```bash
# 1) 実幾何を取得 —— 3ソースをまとめて渡し、スクリプトがコースごとに比較選定
python3 scripts/fetch_olle_osm.py --gpx ~/Downloads/olle-all.gpx --dry   # レポートのみ、ファイルを書かない
python3 scripts/fetch_olle_osm.py --gpx ~/Downloads/olle-all.gpx

# 2) フロントエンド形式に変換、必要なら標高を補完
python3 scripts/import_tracks.py --src tracks/osm --elevation
```

Overpass は 504/429 を返しがちなので、次の 3 つの逃げ道があります：

| フラグ | 用途 |
| --- | --- |
| `--cache-dir scripts/.cache/osm` | クエリのハッシュで応答を保存し、再実行時はディスクから読む。**パラメータ調整中は必須** |
| `--offline` | キャッシュのみ読み込み、決して通信しない。足りないコースはその旨を報告 |
| `--reuse-dir tracks/osm` | relation 側の幾何を既存の `olle-*.geojson` から読み、relations クエリをスキップ |

> ⚠️ `--reuse-dir` は**出所が OSM relation のファイルだけ**を再利用します（`geomSource` フィールドを確認。`both-*` は許可）。
> この判定を外すと前ラウンドの GPX 生成物を relation 側として再利用し、出所ラベルがどんどん曖昧になります。

他所の GPX / KML / GeoJSON も同じです。ディレクトリに入れて実行するだけ（ファイル名に `1` / `01` / `10-1` が含まれていれば番号を認識）：

```bash
python3 scripts/import_tracks.py --src ~/tracks --dry        # まず認識結果を確認
python3 scripts/import_tracks.py --src ~/tracks --elevation  # 取り込み
python3 scripts/import_tracks.py --src ~/tracks --strict     # 未認識ファイルがあれば終了
```

- ファイル名から番号が読めない場合は `--map ファイル名=番号`。OSM の A/B 変種は `--alias 03-A=03`。
- 向きは「隣接コースは端点を共有する」前提で自動補正されます。上書きは `--reverse 01` / `--no-orient`。
  **自動補正は鎖が切れていないときにしか効きません** —— 番号が欠けるとその組が判定漏れするので、取り込み後の「反転」行を必ず確認してください。
- **途切れのある軌跡は「セグメント」として扱います**：地図はセグメントごとに描き**つなぎません**。距離は各セグメントの合計、獲得標高はセグメントごとに累積。
- 間引きは既定で許容差 8 m / 上限 420 点（Douglas–Peucker、予算は全セグメント合算）。
- 公式距離との差が 25% を超えると警告（番号の読み間違いや送迎区間の混入が多い）。書き込む前に確認してください。

## 2. 機能

| モジュール | ページ | できること |
| --- | --- | --- |
| ルート一覧 | `/` | 29 本を番号順表示（3 / 15 号線は A 山線・B 海線が各 1 本）；検索（名称/地域/タグ、「올레 07」「西帰浦」可）、タイプ絞り込み、番号/距離/更新日/名称でソート；上部の行程かごから直接切替；カードからワンクリックでかごに追加 |

> フッター帰属：地図背景 OpenStreetMap、データ出所 **jejuolletrailguide.net**（Jeju Olle Trail 公式英語ガイド）；同サイトはフッターの「友好リンク」にも掲載（外部リンクは常に新規タブ + `rel="noopener noreferrer"`）。友链は `src/App.tsx` の `FRIEND_LINKS`、1 行追加するだけ。

100km の典型的な使い方：本線は平均 15〜20 km、**6 本程度選べば 100 km** に到達；全島を歩き通すなら目標を 430 に。

## 3. データの保存先

| 内容 | 場所 |
| --- | --- |
| ルート / 行程かご / 設定 | `localStorage`（キー接頭辞 `jejuolle100k.`） |
| 出発前チェックリストのチェックとカスタム項目 | `localStorage` の `jejuolle100k.checklist` |
| ローカルアップロード画像 | `IndexedDB`（db `jejuolle100k` → store `images`）、アップロード時に長辺 1600px、JPEG 0.82 に圧縮 |

データはいかなるサーバーにもアップロードされません。デバイス変更やブラウザ消去前に、`/admin` 上部の「JSON エクスポート」でバックアップ；移行後は「JSON インポート」で復元（マージまたは上書き選択可）。

## 4. 距離の計算方法

| シナリオ | 値 |
| --- | --- |
| 事前登録のオルレルート | 公式距離（`manualDistanceKm`）優先、推定しない |
| 自分で作った、未入力のルート | 隣接経由点の直線距離合計 × 1.2（遠回り係数） |
| 獲得標高 | 優先順位は §1「標高と獲得標高の計算方法」（軌跡の標高 > 軌跡沿い補完 > 経路点の手入力標高、手入力「実累積獲得標高」が最優先；なければ「—」） |

行程かご：各ルートを1回のみ計上、全距離の合計を目標と比較し「達成 / N km 不足」を直接表示し、不足に応じて補充可能なルートを提案。

## 5. 地図背景について

地図背景は **Leaflet** で描画、データは **OpenStreetMap**（タイルは OpenStreetMap / OpenTopoMap の公開サービス）由来、世界中カバー、済州の街路/海岸線/地形は正常表示、**API キー不要、設定不要**。

| 背景スタイル | タイル出所 | 特徴 |
| --- | --- | --- |
| 標準地図（デフォルト） | OpenStreetMap `tile.openstreetmap.org` | 道路・POI・地名などの要素が最も充実 |
| 地形図 | OpenTopoMap `tile.opentopomap.org` | 等高線 + 陰影起伏、ハイキング / オフロードの獲得標高判断に適す |

スタイルは「設定」ページでワンクリック切替、即時反映、選択はローカル保存。

- タイルは通信が必要；**オフライン時は地図エリアが空白**、他機能は影響なし。
- **2 種類の線種**（`src/lib/geo.ts` の `mapLineSet()` → `MapLine.approx`）：
  **実線（白枠 + 緑芯）** = `public/tracks.json` の実測軌跡（軌跡のある 27 コース）；
  **灰緑の破線** = 実測軌跡がないコース（通常は自分で作ったもの）、経由点をつないだ**示意線**にすぎず、実際のルートとは見なさないこと。
  詳細ページ、行程かごページとも説明でこの点を明示。
- 極端な場合 Leaflet 初期化失敗は **オフライン示意図**（SVG 投影）に自動降级、クリックで逆ジオコード可能。
- 座標は統一して **WGS-84**（OSM と一致）。済州は中国境外のため、GCJ-02 ずれアルゴリズムは海外では効かず、歴史座標は WGS-84 と等価、背景を替えても位置ずれしない。

> ⚠️ コンプライアンス注意：OpenStreetMap / OpenTopoMap は境外タイル出所、**中国大陸向け測量地図製品には不適**。本プロジェクトは済州島（海外）ハイキングガイドの個人自用作成で、境外タイル使用は問題なし；将来大陸ユーザー向け測量製品として公開する場合は、対象地域をカバーする測量資格を持つ背景サービスに替える必要あり。

## 6. ルート図と表紙

カード表紙は **公式ルートマップ**（1 ルート 1 ページ）、アルバムは **Wikimedia Commons の自由ライセンス写真**。両素材は `public/photos/` に置き、フロントエンド起動時に番号で自動紐付け（localStorage には書かず、ファイルを差し替えれば置換可）。

### 6.1 公式ルートマップ → 詳細ページのアルバム（カード表紙のフォールバック）

Jeju Olle Foundation 公式「Route Map」PDF をルートごとに画像へ分割、1 ルート 1 ページ：

```bash
# デフォルトは ~/Downloads/171011_jeju-olle-route-map.pdf を読む
python3 scripts/split_route_map.py
python3 scripts/split_route_map.py --pdf /path/to/route-map.pdf
python3 scripts/split_route_map.py --limit 2      # まず 2 件切って効果確認
```

| 出力 | 説明 |
| --- | --- |
| `public/photos/maps/olle-<番号>.webp` | **詳細ページ原本**：1 ルート 1 ページ全体（1432×1012、約 100KB/枚、26 枚計 2.5MB）、アルバムとライトボックス用 |
| `public/photos/maps/cover/olle-<番号>.webp` | **カード表紙（圧縮版）**：760×537、約 25KB/枚、26 枚計 0.65MB |
| `public/photos/maps.json` | 番号 → `{ file: 原本, cover: 表紙 }`、フロントエンドが読んで `cover` を設定し原本をアルバムに追加（全サイズ表示可） |

**なぜ 1 画像から 2 サイズ出すか**：カード表紙は一覧で約 300–400px 幅しか描画されず（`.cards` は `minmax(min(300px,100%),1fr)`）、1432px 原本をそのまま入れるのは無駄 — トップ 26 枚で 2.5MB 読み込む。表紙を別圧縮したら初回は 0.65MB に、詳細/ライトボックスは従来どおり 1432px 原本を表示し拡大して地名を読んでも影響なし。

圧縮は **ローカル** で実施（Pillow リサイズ + WebP 品質低下、`--cover-width` / `--cover-quality` 調整可）、TinyPNG / tinyimg などのオンラインサービスと同類だが API キー不要、第三者への画像アップロード不要、再現可能。オンラインサービスに替えても、`maps/cover/` の同名ファイルを上書きすればよい。

決まりごと：

- **トリミングしないこと**。公式ページは 842×596 横版、地図がページ全体に広がる；上下 30% を切るとルート本体を切る（01 の南端、10-1 の済州本島側が切れる）。表紙側の `.route-cover` は `aspect-ratio: 842 / 596` でページ比を維持しゼロトリミング。
- **ページ番号 ↔ ルート番号は要確認**。`PAGE_CODES` は各ページ右下の太字ルート番号で整理（PDF 1 ページ目は表紙、2〜27 ページがルート）。新版 PDF に替える際はこの表を再確認せねばならず、さもないとルート番号がずれる。
- この 2017.10 版には **Route 18-2（下楸子島）のページがない**ため、18-2 は「図なし」プレースホルダー。
- 表紙優先順位：**管理者が設定した表紙 > 公式ルートマップ > Commons 写真**。自分の写真にするには `/admin` の「基本情報」でアップロード。

> ⚠️ 公式ルートマップの著作権は **© Jeju Olle Foundation** に帰属、PDF 内ページに「無断の商業的複製・転載・配布禁止」と明記。本プロジェクトは個人自用作成で非商業、アルバム/ライトボックスとも帰属 `credit` を表示；**商用利用しないこと**。

### 6.2 カード表紙（風景写真、Wikimedia Commons 自由ライセンス）

小紅書などの画像は著作権がありスクレイピング禁止、**プロジェクトに一括ダウンロードしないこと**。本プロジェクトは代わりに Wikimedia Commons の自由ライセンス作品（CC0 / CC-BY / パブリックドメイン）を使用。

```bash

python3 scripts/fetch_photos.py            # 全件
python3 scripts/fetch_photos.py --limit 2  # まず 2 件試す
python3 scripts/fetch_photos.py --dry      # 検索のみ、ダウンロードしない
```

スクリプトの出力：

| ファイル | 役割 |
| --- | --- |
| `public/photos/olle-<番号>.jpg` | 写真（長辺 1600px） |
| `public/photos/manifest.json` | 番号 → 画像のマッピング、起動時に読んで対応ルートへ紐付け（localStorage には書かず、ファイル差し替えで置換） |

> この対応は**コース番号がキー**。番号を変えたら必ずキーも同期すること（03 / 15 を A/B に分割した際に漏れると、該当コースの表紙と公式ルート図が丸ごと消える）。

> 注意：写真は「そのルートの通る場所」の示意写真、**公式ルートの公式撮影ではなく**、**実測軌跡でもない**。ガイドの根拠にするなら公式資料と自身の実写を頼ること。
> 不適切な写真は：`public/photos/` 配下の該当ファイルと `manifest.json` の項目を削除すればよい。

## 7. 出発前準備ページのデータ境界

`/prep` の内容はオルレ公式サイト（jejuolle.org）、韓国観光公社の公開資料、公開旅行記を参考に 2026-09 に整理し、`src/lib/prep.ts` に記述。

- **政策類項目は「出発前再確認」とマーク**（赤小タグ）：ビザ免除の範囲、K-ETA 要否、IDP レンタカー、緊急電話は変わるため、出発前に再確認。
- **オルレパスポートは出発前再確認項目ではない**：済州到着後に観光案内所やコース起点近くの店で現地購入する小冊子（約 ₩20,000、現金を用意）。価格は現地の表示どおりで、出発前に調べる必要はない。
- **価格は一般的な幅のみ**、予算見積もり用、予約プラットフォームと店舗の最新情報に準拠。
- **具体店名・ホテル名は書かない** — 未確認の名前は作らず、Kakao Maps / Naver Maps で自身で評価を。
- **バス・決済の操作詳細**（T-money カード発行手数料と乗継ぎ、iOS 発行制限、STOP ベルと通過、Uber 対面払い等）は実体験と公開旅行記由来、公式条項ではなく変化が早く、ページ内で赤文字注意と参照リンク付き。
- レンタカー項目は重点注意：韓国は短期滞在者に 1949 ジュネーブ条約紙の IDP を求め、**中国大陸の運転免許は IDP 発給対象外**のため、実務上多くの店が受付けない。自転走には店と書面で事前確認を。
- **女性/男性 よく使うリスト**は「何を持つか、なぜ持つか」の経験的助言、**政策・価格の断言を含まない**；液体容量や保安検査（爪切りは預け荷物推奨）などの硬い規定は `note` に通常枠で注意書きとし、約束としない。両リストの文案は公式 43 項目と意図的に重複させず — さもないと重複排除ロジックに「既にリストにあり」と判定され白書き同然。

### チェックリストのチェック / スキップ状態マシン

`jejuolle100k.checklist`（`src/lib/storage.ts` の `ChecklistState` 参照）は 4 つの相互排他な id 集合を管理：

| 状態 | フィールド | 意味 |
| --- | --- | --- |
| 準備済み | `checked` | チェックした項目、進捗に計上 |
| スキップ済み | `skipped` | 手動スキップ項目、**進捗分母にも未完了にも計上せず**、通常は表示（灰色 +「スキップ」タグ、ワンクリック「復元」） |
| カスタム | `custom` | 自身が追加した項目（`PrepItem[]`） |
| プリセット追加済み | `extras` | 「女性/男性 よく使うリスト」から選んだ項目（`PrepItem` より `from` が 1 つ多い `ChecklistExtra[]`） |

- 項目をチェックすると `skipped` から自動削除（排他）；スキップするとそのチェックを自動解除。
- 「未完了のみ」はチェック済みとスキップ済みを両方隠す；通常モードではスキップ済みも表示し復元しやすく。
- 「グループ全選択」はスキップされていない項目のみに作用、スキップ済みを再チェックしない。
- 進捗バーと各グループの `done/total` は「スキップされていない」項目のみで計算。

### プリセットリスト（女性/男性）のマスターリスト組込み

データ出所は `src/lib/prep.ts` の `PREP_PRESETS`（2 セット独立 id：`preset.f.*` / `preset.m.*`）。
これらは **デフォルトリストではなく**、単なる候補プール：`extras` が空ならページに何も追加されず、ユーザーがいくつか選んだ時だけ「プリセットリスト追加済み」グループが出る。

| 操作 | 挙動 |
| --- | --- |
| 単発「追加」/「削除」 | `extras` の 1 件を書く/消す、トグル同等、再確認なし |
| 「すべて追加（N）」 | `ids` 省略 → 丸ごと統合；ボタン上の N は**重複排除後の実追加件数** |
| 「すべて削除」 | マスターリストから丸ごと削除（Confirm 経由、これら項目のチェック/スキップ状態も連動消去のため） |
| 「リストリセット」 | `checked / skipped / custom / extras` 全消去 |

重複排除基準（`addPresetItems`）：**id で「この件追加済みか」、 `normItemText(text)` で「リストに同じことが既にないか」を判定**（全空白と大小文字を無視）。該当項目は再書き込みせず、セレクターでは「既にリストにあり」と表示してボタン削除。公式グループに同じものが既にある場合も再追加しない — ゆえに両リストの文案は公式 43 項目と意図的重複なし。

⚠️ 重複排除は `setChecklist(prev => ...)` の updater 内で `prev` を基準に計算せねばならず、描画期の `checklist` で判定してはいけない：「追加」を連打すると描画期スナップショットは古く、同じ件を繰り返し書く。同様に、updater が新規なしなら `prev` 元オブジェクトを返し（React は再描画をスキップ、localStorage 書き込みも無駄にしない）。

## 8. エラー時も白紙画面にしない

二層 `ErrorBoundary`（`src/components/ErrorBoundary.tsx`）：

| 層 | 位置 | 捕捉するもの |
| --- | --- | --- |
| 全体 | `main.tsx` が `<App />` を包む | Router / Provider 自身が落ちてもページあり |
| ページ | `App.tsx` 内容部、`key` を pathname に绑定的 | 単ページ崩壊でも上部ナビ残り、別ページに切替て継続可；ルート変更でエラー状態自動リセット |

エラーページ提供：再試行 / ホームへ / エラー情報コピー / コンポーネントスタック展開 / **ローカルデータ消去して再読込**（データに壊れレコードがある時の最終手段、自作 Modal 二段確認）。

⚠️ 捕捉するのは **描画期** エラーのみ。イベントコールバック、`setTimeout`、リクエストコールバック内の非同期エラーは React に上浮かず（「クリックしても反応なし」、白紙にならず）。
`DataProvider` のデータ読込は `requestAnimationFrame` 内で走り、例外も React に上浮かない — そこは別途描画期投擲に変換して境界へ渡し、スケルトン画面での仮死を避ける。

## 9. デプロイ（Docker + nginx + Dokploy サブパス）

プロジェクトは **純静的フロントエンド**（`HashRouter` + `base: './'`）、バックエンドなし、`asset-system-frontend` パラダイムに倣い nginx 静的イメージとしてパッケージ、`/jeju/` サブパス下に配置、Dokploy の Traefik が PathPrefix で振り分け。

### 主要ファイル

| ファイル | 役割 |
| --- | --- |
| `Dockerfile` | 多段ビルド：node 依存インストール + `npm run build`、成果 `dist/` を nginx の `/usr/share/nginx/html/jeju` にコピー |
| `nginx.conf.template` | nginx:alpine 起動時に `templates/*.template` を envsubst で `conf.d/default.conf` に描画；本テンプレートは `/jeju` → `/jeju/` リダイレクト + 静的ホスト + SPA フォールバックのみ |
| `.dockerignore` | node_modules / dist / .git / ローカルスクリプトキャッシュを除外、ビルドコンテキスト縮小 |
| `.npmrc` | npmmirror でコンテナ内 `npm ci` を高速化 |

> `HashRouter` + `base: './'` のため、`dist/` リソースは相対パス、`/jeju/` 下で `vite.config.ts` の変更不要、history ルートの rewrite も不要。

### ローカルでイメージをビルド・自己検証

```bash
docker build -t jeju-olle-100k .
docker run --rm -p 8080:80 jeju-olle-100k
# ブラウザで http://localhost:8080/jeju/ を開き検証
```

### Dokploy へ push

1. Dokploy で **Application** を新規作成、ソースは GitHub 公開リポジトリ `tanabalu/jeju-olle-100k`（main ブランチ）に接続。
2. ビルド方式は **Dockerfile** を選択（多段は既に記述、追加パラメータ不要）。
3. ポート：コンテナは `80` を公開、Dokploy 内ポートは `80` を填入。
4. **Traefik ルート規則**（PathPrefix）：`Path(\`/jeju\`) || PathPrefix(\`/jeju/\`)` を使い、`/jeju` のパス区間だけに一致させます。同一ホストの Pages パス `/jeju-olle-100k/` が Dokploy に取られるのを防ぎます。
5. デプロイ後は `https://your-domain/jeju/` にアクセス（「your-domain」を実際のサブパス宿主ドメインに置換）。

> サブパス変更時は 2 か所：`Dockerfile` の `COPY ... /usr/share/nginx/html/<新パス>` と `nginx.conf.template` 内の `/jeju`、`/jeju/`、`/jeju/index.html`。

## 11. 既知の境界

- **軌跡は二手データ**：29 コース中 28 は OSM / GPX 由来、`15-B` は OSM 路網からの推定で、**公式のルート変更には自動で追従しません**。
  画面の距離は常に `SPECS` の公式値を用い、「軌跡実測 X km」を併記します。±5% を超えるのは 13 コース、
  うち **`15-A`（+19.0%）と `08`（−11.9%）は ±10% 超** —— この2コースの**獲得標高と地図形状**は割り引いて見てください。
