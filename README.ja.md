# 済州オルレ・100km ガイド（済州島 Jeju Olle Trail）

## 概要

済州島の 27 本のオルレ（올레길）を自分の行程にまとめ、距離を自動計算して 100km を達成できるか確認したり、出発点・到着点、沿道の宿泊施設、景色、アルバムを管理したりできます。

純フロントエンド。データはローカルブラウザ（localStorage + IndexedDB）に保存されます。依存関係は npm で管理し、エンドユーザーは `npm run build` が出力する静的サイトを使います。

> 要点：**地図背景データは OpenStreetMap 由来で、世界中カバーされ、API キー不要**。済州の街路・海岸線・地形は正常に表示されます。オフライン時は地図エリアが空になりますが、距離計算などのコア機能には影響しません。§5 参照。

## 1. あらかじめ登録されるもの

初回起動時に、公式の **27 本のオルレ**（出典：jejuolle.org）が自動的に書き込まれます：

- **本線 21 本 + 支線 6 本**（1-1 牛島、7-1、10-1 加波島、14-1、18-1 上楸子、18-2 下楸子）
- 公式距離は「実際の距離」に格納済みなので、**距離は公式値を優先**、直線推定はしません
- 公式難易度 Low / Medium / High は 2 / 3 / 4 つ星にマッピング済み
- 本線は 1 本 10.1～20.9 km。27 本の合計は **403 km**（`OLLE_TOTAL_KM` は `SPECS` から導出、ハードコードなし — ホームの「437km 27코스」は宣伝上の数値。下の「公式距離には版がある」参照）

| データ出所 | 正確性 | 自分で補う必要があるもの |
| --- | --- | --- |
| 路線番号、出発/到着名称、公式距離、公式難易度 | 公式サイト、そのまま利用可 | — |
| 出発/到着の緯度経度 | **町レベルの近似座標、公式の実測軌跡ではない** | `scripts/import_tracks.py` で実軌跡を一括置換、または管理画面の地図でのクリックで補正 |
| 標高と累積獲得標高 | **SRTM 30m 地形を近似経路に沿ってサンプリングした推定値、公式の実測ではない** | 実 GPX をインポート後、軌跡に沿う点ごとの累積に自動切替（より正確） |
| カード表紙 | **公式ルートマップページ**（© Jeju Olle Foundation）、26 路線に画像あり、18-2 のみ公式ページなし | 自分の写真にするには `/admin` の「基本情報」でアップロード |
| 宿泊、見どころ、アルバム | 空で事前登録 | `/admin` で入力 |

### 獲得標高の計算方法（重要）

事前登録ルートの標高列は `scripts/fetch_elevation.py` が opentopodata.org の公開 **SRTM 30m** データセットから取得し、`src/lib/olleeElevation.ts` に格納されます（ビルド時にバンドル、実行時は通信しません）。

- **非環状路線**：「出発→到着」の直線に均等サンプリング（各 20～43 点）
- **環状路線**（牛島 / 加波島 / 上下楸子）：公式距離から逆算した円周サンプリング
- 獲得標高は隣接点差に **3m ヒステリシス閾値**を適用し、地形データ自体の揺らぎを抑えます

⚠️ これは **推定値であり、公式の実測獲得標高ではありません**：実際の路線は海岸沿いに曲がりくねり、海岸の小丘を越えるため、直線サンプリングでは拾えず、実際の獲得標高は通常表示より大きくなるのが普通です。27 本の合計は約 2230 m — 「どちらがきついか」の順位付けには使えますが、ペース配分や補給計画には実軌跡を使ってください（次節；インポート後は獲得標高が軌跡ベースに自動切替）。

このデータを更新するには：

```bash
python3 scripts/fetch_elevation.py            # 全件再取得（ローカルキャッシュあり、欠落分のみ補完）
python3 scripts/fetch_elevation.py --limit 2  # まず 2 件試して効果を確認
python3 scripts/fetch_elevation.py --force    # キャッシュ無視で全件再取得
```

自分で作ったルートにはサンプリングデータがなく、`/admin` の「経由点」で各点に標高を入力します；**標高を持つ点が 2 未満の場合、獲得標高は 0 ではなく「—」と表示**（0 だと平坦だと誤解させるため）。

### 1.3 近似座標を実軌跡で置換（開発ログ — 中国語のみ）

> ⚠️ **dev log, zh only.** 以下のセクションは中国語のまま残しています。原本は `README.md` §1.3 参照。
>
> 预置坐标是**城镇级近似**，落在地图上是「大概这一带」，用来排序和看分布没问题，
> 但**导航、算补给、算真实爬升都不该用它**。
>
> #### 轨迹从哪来（**三个数据源，逐条比选，谁可信用谁**）
>
> | 源 | 能拿到什么 | 怎么拿 |
> | --- | --- | --- |
> | ① **OSM 的 route relation** | 整条线的真实走向。但偶来在 OSM 里**只建了一部分**关系 | `fetch_olle_osm.py`（默认） |
> | ② **OSM 里名字带编号的散 way** | **没有关系的那几条线（12/13/14/15 等）在这里** | `fetch_olle_osm.py`（默认，自动） |
> | ③ **按课程分段的整条偶来 GPX** | 25 条课程轨迹，**首尾严格相接**，覆盖 01–21 + 3A/3B/7-1/10-1/14-1 | `fetch_olle_osm.py --gpx <文件>` |
> | 官方 jejuolle.org | 起终点 GPS + 里程表（**没有中间走向**） | 官网；`seed.ts` 的 `SPECS` 就是它 |
> | Wikiloc / AllTrails | 单条路线的个人 GPS 轨迹（带真实海拔） | 注册后下载 GPX |
> | 你自己走 | 最真实 | 手机记录导出 GPX |
>
> > ⚠️ **只看 ① 会得出完全错误的结论。** 本项目一度就是这么错的：按 relation 判定
> > 「12、13、14、15、17、21 在 OSM 里没有数据」——**relation 确实没有，但散 way 有**。
> > 全岛 `highway` + 名字含「올레 / Olle」的 way **722 条**，12 有 77 条、13 有 74 条、15 有 96 条。
> > 前端当时只能把 `seed.ts` 的**城镇级近似坐标**连成一根斜穿岛内的直线 —— 就是地图上那根
> > 从西南直插东北的假线。**判断「某个源没有」之前，先把别的源都查一遍。**
>
> ##### 三个坑（都踩过，都静默）
>
> 1. **两套命名习惯覆盖同一段路**：`올레길 12`（韩文，零散 7 条）与 `Ollegil 12`（英文，完整 70 条）。
>    混在一个池子里缝 = 同一段路喂两遍（12 只能画出 43%）。`named_ways()` 按 **(编号, 命名习惯)** 分组。
> 2. **`Ollegil N` 几乎全是 `footway`**（12 号：73 条 footway + 4 条 unclassified，中位 138m），
>    只覆盖离路段步道，被村道隔成 16 段 —— **光靠散 way 也拼不出完整线路**（这是 ③ 存在的理由）。
> 3. **`<trkpt lat=".." lon="..">` 是 lat 在前**。解析时读成 `(lng, lat)` 才对，摆反**不报错**，
>    但里程全是垃圾（实测 374.6km，正确值 384.6km）。
>
> ##### OSM 覆盖实况（2026-09-28 实测）
>
> - 框内 `route=hiking` 关系共 **25 个**，其中名字含「올레」的 **20 个**；另外 3 个是汉拿山登山道
>   （관음사코스 / 사라오름코스 / 성판악코스）—— 加 `--broad` 复查过，没有漏掉偶来的线。
> - 能用的 relation 覆盖 **01–06、08–11、16、18、19、20**。
> - **12、13、14、15、17、21 没有 relation**，靠 ②③ 补；离岛支线：**01-1（牛岛）已补真实海岸环线**——
>   OSM `우도해안길` 海岸路，桥接 89m 缺口 → **12.0km 连续环线**（官方 13.2km，差 −9%）；
>   **18-1（上楮子）已补真实步道片段**——OSM `올레길 18-1` 的 25 条步道缝成 **9 段**，
>   段间缺口最大 3.5km，前端按段画、缺口留空不连线；片段总长 14.5km 比官方 11.4km 长，
>   因含绕行/观景点支线，**里程标签仍以官方 11.4km 为准**；
>   **18-2（下楮子）三源（relation / 散 way / GPX）均无数据，仍保持「示意虚线」**。
> - **07 的两套几何都是「改线前」的旧走向，都不能用**：OSM relation 19.80km（154%）、
>   hikeonearth 的 GPX 段 12.75km（98%，**光看里程完全看不出问题**）—— 两者的终点都落在**月坪**，
>   拿官方 GPS 端点一卡就露馅。官方**现行** 7 线是「제주올레여행자센터 → 서귀포버스터미널 **12.9km**」
>   （对应 2026-07-01「7코스 법환포구 구간 변경」）。所以 **07 保持「示意虚线」**，
>   等拿到 2026-07 之后的单条 GPX 再导入替换。
>
> > ⚠️ **OSM / GPX 都是历史快照，官方改线它不会自动跟上**。官方站会发「코스 구간 변경」公告
> > （例：2026-07-01「제주올레 7코스 법환포구 구간 변경」）。拿走向前先核官方里程差得不离谱。
>
> OSM 是众包数据：走向大体准确（都是照着指示带走过的），但**关系里的 way 是无序集合**，
> 还常有缺口（少画一段、被拆成父子关系、A/B 变体并存）。`fetch_olle_osm.py` 因此做了五件事：
>
> 1. **缝合按节点级匹配**，不是只看端点 —— 一条长 way 的中途节点被别的 way 接上是常态，
>    只比端点会把它误判成断口，图上凭空多出一段跳线。岔路口按**直行优先**选下一段。
> 2. **接不上就收尾分段，不用直线硬连**。段与段之间就是 OSM 真没画的地方，导出成
>    `MultiLineString`，前端按段画 → 地图上是**真的缺口**，不伪造。
>    被拆成「父关系 + 子关系」的线，`out geom` 不会递归下去，脚本会**按 id 精确补一次**
>    （不依赖 `rel(br.r)`，因为部分镜像不支持它、直接回 400）。
> 3. **拒绝「闭合旁路」**：如果走完候选 way 会落回链子**内部**已经走过的节点，说明它是
>    一条绕一圈回到原路的**替代支线**（OSM 常把 A/B 变体、无障碍路线塞在同一个关系里），
>    不是一个「往前走」的候选。这类段会被剔出几何与里程，报表如实写明剔了多长；
>    加 `--keep-parallel` 可保留原样。**实测证据只有 03**（剔前 29.76km/142% → 剔后 22.71km/109%）
>    与 05（15.33→14.60，剔 0.74km）—— 别拿它解释所有超长。
> 4. **段内折返单独报数**：同一节点在一段里被走了两次 → 中间那几公里是白走的，而且
>    **剔不掉**（它长在这一段里面），报表会给出「折返 N 处 / 共 X km」。
>    剩下的判断交给地图：要么这条线在 OSM 里本就含往返段（观景台来回），要么缝合走岔了。
> 5. **三个数据源逐条比选，打分不看里程长短**：`RANK = ✅0 / ⚠️1 / ⛔2 / —3`，
>    同档比**断口总长**，再平手才比「覆盖更接近 1.0」。
>    候选来源写着 `relation` / `ways-ko` / `ways-en` / `gpx` / `both-xx`，
>    报表里 `*` 标出选中的那个，落选的也全列出来（含里程/断口/判定）。
>    ⚠️ **只比里程长短会选错**：更长的那个往往只是混进了替代支线或邻线延伸。
> 6. **补缺只「补缺」，不取并集**：`uncovered_ways()` 只剪出 base 上真没有的那几段，
>    并且**逐套命名分别做**（同一段路在韩文名 / 英文名 / GPX 里各有一份，混起来缝就是重复）。
>    另有一道不变量：**合并结果不得比 base 短**（`add_merge`），否则放弃该候选并写明原因。
> 7. **报表给出每条的判定**：`✅ 可用 / ⚠️ 有缺段 / ⛔ 不可用`，看三条：
>    「实走 ÷ 官方」**<60%**（只画了一半）、**>130%**（走向与官方里程不符）、
>    「断口占比」**>35%**。⛔ 的不导出 —— 宁可这条线保持「近似」，
>    也不给它半条线、或走向对不上的线冒充。想连 ⛔ 的一起导就加 `--keep-bad`，
>    只关掉「超长」这道闸就加 `--max-coverage 0`。
> 8. ⭐ **第 4 道闸门：官方 GPS 端点校验**（`endpoint_verdict`，容差 2km）。
>    **里程对了 ≠ 走向对了** —— 实测 GPX 里的 07 段是 12.75km / 99%，看着完美，
>    但终点离官方「西归浦巴士总站」4.8km，走的是另一条线。只靠里程闸门拦不住这种。
>    端点取自 `seed.ts` 里标了 `// 官方 GPS` 的两个点 + `SPECS` 的起终点。
> 9. **明确排除清单**（`SKIP`）：现有几套几何**没有一套能拼成连贯的线**时，宁可留示意虚线。
>    目前只有 `14-1`（散 way 缝出来 4 段首尾乱跳；GPX 段 189% 超长）。
>    **故意写成「对某一条线的判断」而不是继续调阈值** —— 阈值是全局的，为一条线放宽会连带影响另外 20 多条。
>
> > ⭐ **一条极灵的判伪口径**：**实走里程 ≤ 官方里程**。一条线不可能比它自己长。
> > 倒挂只有三种原因，诊断区会分开报：
> > ① 替代支线/变体混进关系（**并联段**，两端挂回主线）→ 剔掉；
> > ② 段内折返（**同一节点走两次**）→ 剔不掉，只报数；
> > ③ **这个源映射的根本不是那条线**（官方已改线、OSM 还留着旧走向）→ 几何完全自洽，
> > 内部一致性检查查不出来，**只能靠里程倒挂发现**（实测 07 的 relation = 154%）。
> >
> > ⚠️ **但它的前提是基准本身是对的。** 官方里程只在 `src/lib/seed.ts` 的 `SPECS` 里存一份
> > （网页上给用户显示的就是它），脚本从那里读（`load_official_km`，解析不出来就大声报错）。
> > 脚本里曾手抄过一份副本，写着 09=8.0（官方 12.3）、18=19.8（官方 17.1）、15=19.0（官方 15.5），
> > 13 条是旧资料口径 —— 结果把 99% 正常的 **09 判成「153%、比官方长」**，白查了一轮缝合算法。
> > **判「超长」之前，先用官方站的里程表核一遍基准。**
>

> #### 走向会自动校正（`import_tracks.py`）
>
> **方向 = 行进方向**，不是装饰：详情页の「起点 → 终点」坐标、剖面の爬升/下降都按它读，
> 反了会把上坡读成下坡，起点坐标还会贴到另一端去。而**拼接时不看成员顺序，方向本来就是随机的**
> （见上面「缝合算法」の警告），所以必须校正。
>
> 校正靠一条结构事实，不需要任何外部坐标：
>
> > 偶来 27 条**首尾相接**：课程 N の终点 = 课程 N+1 の起点（`seed.ts` の `SPECS` 写死的）。
>
> 于是相邻两条课程在 OSM 里必然共享一个端点节点，共享点应当落在「N の终点 / N+1 の起点」上；
> 若落成「N+1 の终点」，则这一对里**有且仅有**一条被反着拼了。谁错 —— 取**翻转条数最少**の解。
> 两个好处：
>
> - **数据源本身没问题时它给出 0 次翻转**，不会误伤一份方向本来就対の Wikiloc GPX；
> - 实测 2026-09-28 の 23 条里判出 `06 / 11` 两条反向（`05↔06`、`10↔11` 共享の端点落成
>   「终点对终点」），导入时已自动翻回。**判得对**：这两条の几何来自 relation 侧（方向随机），
>   而 05、10 来自 GPX（方向本来就是官方的）；翻转后 06 = 「牛沼河口 → 独立岩」、
>   11 = 「摹瑟浦 → 武陵」，与官方一致。
> - 复核手段：拿 GPX（官方走向）当基准，逐条比「导入後の首点 ↔ GPX 首点 / 末点 ↔ GPX 末点」。
>   23 条全部同向。

> | `--gpx FILE` | **第三个数据源**：按课程分段的整条偶来 GPX。12/13/14/15/17/21 这些没有 relation の线靠它 |
> | `--broad` | 不带名字过滤再查一遍框内 hiking 关系，把「OSM 真没建」和「建了但名字没匹配上」分开 |
> | `--keep-parallel` | 不剔除并联段（默认剔除，否则里程会比官方还长） |
> | `--max-coverage 1.25` | 收紧「比官方长」这道闸（默认 1.30 一票否决） |
> | `--keep-bad` | ⛔ 与 `SKIP` 里的也照导（默认跳过） |
> | `--alias 15-B=15` | 变体编号映射到你的编号（`03-A=03` 已内置为默认，见 `DEFAULT_ALIAS`） |
> | `--bridge M` | ≤M 米の两段用**直线**接起来（默认 0 = 不接）。本项目不用，理由见上 |
>
> 拿到别处的 GPX/KML 也一样，丢进一个目录直接导：
>
> ```bash
> # 文件名带路线编号即可（1 / 01 / 10-1 都认）
> python3 scripts/import_tracks.py --src ~/Downloads/jeju-olle-tracks --elevation
> python3 scripts/import_tracks.py --src ~/tracks --dry        # 先看识别结果
> python3 scripts/import_tracks.py --src ~/tracks --strict     # 有未识别文件就退出
> ```
>
> - 文件名认不出编号の用 `--map 文件名=编号` 指定。**走向默认会按「相邻课程首尾相接」自动校正**
>   （见上面那节），要手工指定方向或关掉自动判定用 `--reverse 01` / `--no-orient`。
>   OSM 里的 A/B 变体（`3코스-A`、`15코스-B`）用 `--alias 03-A=03` 手工归到你的编号。
> - **有断口の轨迹按「分段」处理**（GPX 多个 `<trkseg>`、KML 多个 `<coordinates>`、
>   GeoJSON の `MultiLineString`）：段与段之间是数据真空，
>   - 地图按段画，**不连线**，缺口就留缺口；
>   - 里程是各段之和，**爬升逐段累加** —— 跨段那截海拔未知，混着算会凭空多出一大截；
>   - `tracks.json` 里段数 > 1 才写 `segments`，前端据此走多段绘制。
> - 落盘结果是 `public/tracks.json`，**运行时 `fetch` 读取，不进 localStorage**，换轨迹直接替换文件即可。
> - 有轨迹の路线，地图按真实轨迹画线、起终点吸附到轨迹首末点；
>   **累计爬升与海拔区间改按轨迹逐点累加**（标高提示变为「取自真实轨迹」）；
>   里程仍**以官方值为准**，详情页同时给出「轨迹实测 X km」便于对照。
>   没轨迹の仍走原来の近似逻辑，互不影响。
> - 轨迹抽稀默认容差 8 m / 上限 420 点（Douglas–Peucker，**预算按所有段合计算**），既保形状又不让产物膨胀。
> - 与官方里程偏差 >25% 会告警（多半是编号认错、轨迹含接驳段，或 OSM 那块没画完），先核对再落盘。
> - 只有轨迹没海拔也能用：总里程照算，爬升显示「—」并提示「暂缺海拔数据」；
>   加 `--elevation` 就用 opentopodata の SRTM 30m 补上（同一份数据源口径与预置剖面一致，结果有缓存）。

## 4. 距離の計算方法

| シナリオ | 値 |
| --- | --- |
| 事前登録のオルレルート | 公式距離（`manualDistanceKm`）優先、推定しない |

## 5. 地図背景について

地図背景は **Leaflet** で描画、データは **OpenStreetMap**（タイルは OpenStreetMap / OpenTopoMap の公開サービス）由来、世界中カバー、済州の街路/海岸線/地形は正常表示、**API キー不要、設定不要**。

| 背景スタイル | タイル出所 | 特徴 |
| --- | --- | --- |
| 標準地図（デフォルト） | OpenStreetMap `tile.openstreetmap.org` | 道路・POI・地名などの要素が最も充実 |
| 地形図 | OpenTopoMap `tile.opentopomap.org` | 等高線 + 陰影起伏、ハイキング / オフロードの獲得標高判断に適す |

> ⚠️ タイル出所選択の注意：**CARTO は使わないこと**（`basemaps.cartocdn.com`）— 匿名リクエストに「API key required」透かし入りタイルを強制し、自前のキーが必要になる。OSM / OpenTopoMap の公開サービスが本当にキー不要。

スタイルは「設定」ページでワンクリック切替、即時反映、選択はローカル保存。

- タイルは通信が必要；**オフライン時は地図エリアが空白**、他機能は影響なし。
- **2 種類の線種**（`src/lib/geo.ts` の `mapLineSet()` → `MapLine.approx`）：
  **実線（白枠 + 緑芯）** = `public/tracks.json` の実測軌跡；**灰緑の破線** = まだ実測軌跡がないもの、
  `seed.ts` の近似座標をつないだ**示意線**（ずれは最大 10km、ルートと見なさないこと）。
  詳細ページ、行程かごページとも説明でこの点を明示。
- 極端な場合 Leaflet 初期化失敗は **オフライン示意図**（SVG 投影）に自動降级、クリックで逆ジオコード可能。
- 座標は統一して **WGS-84**（OSM と一致）。済州は中国境外のため、GCJ-02 ずれアルゴリズムは海外では効かず、歴史座標は WGS-84 と等価、背景を替えても位置ずれしない。

> ⚠️ コンプライアンス注意：OpenStreetMap / OpenTopoMap は境外タイル出所、**中国大陸向け測量地図製品には不適**。本プロジェクトは済州島（海外）ハイキングガイドの個人自用作成で、境外タイル使用は問題なし；将来大陸ユーザー向け測量製品として公開する場合は、対象地域をカバーする測量資格を持つ背景サービスに替える必要あり。

## 6. ルート図と表紙

カード表紙は **公式ルートマップ**（1 ルート 1 ページ）、アルバムは **Wikimedia Commons の自由ライセンス写真**。両素材は `public/photos/` に置き、フロントエンド起動時に番号で自動紐付け（localStorage には書かず、ファイルを差し替えれば置換可）。

### 6.1 公式ルートマップ → カード表紙

Jeju Olle Foundation 公式「Route Map」PDF をルートごとに画像へ分割、1 ルート 1 ページ：

```bash
# デフォルトは ~/Downloads/171011_jeju-olle-route-map.pdf を読む
python3 scripts/split_route_map.py
python3 scripts/split_route_map.py --pdf /path/to/route-map.pdf
python3 scripts/split_route_map.py --limit 2      # まず 2 件切って効果確認
```

| 出力 | 説明 |
| --- | --- |
| `public/photos/maps/olle-<番号>.webp` | **詳細ページ原本**：1 ルート 1 ページ全体（1432×1012、約 100KB/枚、26 枚計 2.5MB）、アルバムとライトボックス用 |
| `public/photos/maps/cover/olle-<番号>.webp` | **カード表紙（圧縮版）**：760×537、約 25KB/枚、26 枚計 0.65MB |
| `public/photos/maps.json` | 番号 → `{ file: 原本, cover: 表紙 }`、フロントエンドが読んで `cover` を設定し原本をアルバムに追加（全サイズ表示可） |

**なぜ 1 画像から 2 サイズ出すか**：カード表紙は一覧で約 300–400px 幅しか描画されず（`.cards` は `minmax(min(300px,100%),1fr)`）、1432px 原本をそのまま入れるのは無駄 — トップ 26 枚で 2.5MB 読み込む。表紙を別圧縮したら初回は 0.65MB に、詳細/ライトボックスは従来どおり 1432px 原本を表示し拡大して地名を読んでも影響なし。

圧縮は **ローカル** で実施（Pillow リサイズ + WebP 品質低下、`--cover-width` / `--cover-quality` 調整可）、TinyPNG / tinyimg などのオンラインサービスと同類だが API キー不要、第三者への画像アップロード不要、再現可能。オンラインサービスに替えても、`maps/cover/` の同名ファイルを上書きすればよい。

決まりごと：

- **トリミングしないこと**。公式ページは 842×596 横版、地図がページ全体に広がる；上下 30% を切るとルート本体を切る（01 の南端、10-1 の済州本島側が切れる）。表紙側の `.route-cover` は `aspect-ratio: 842 / 596` でページ比を維持しゼロトリミング。
- **ページ番号 ↔ ルート番号は要確認**。`PAGE_CODES` は各ページ右下の太字ルート番号で整理（PDF 1 ページ目は表紙、2〜27 ページがルート）。新版 PDF に替える際はこの表を再確認せねばならず、さもないとルート番号がずれる。
- この 2017.10 版には **Route 18-2（下楸子島）のページがない**ため、18-2 は「図なし」プレースホルダー。
- 表紙優先順位：**管理者が設定した表紙 > 公式ルートマップ > Commons 写真**。自分の写真にするには `/admin` の「基本情報」でアップロード。

> ⚠️ 公式ルートマップの著作権は **© Jeju Olle Foundation** に帰属、PDF 内ページに「無断の商業的複製・転載・配布禁止」と明記。本プロジェクトは個人自用作成で非商業、アルバム/ライトボックスとも帰属 `credit` を表示；**商用利用しないこと**。

### 6.2 アルバム写真（Wikimedia Commons 自由ライセンス）

小紅書などの画像は著作権がありスクレイピング禁止、**プロジェクトに一括ダウンロードしないこと**。本プロジェクトは代わりに Wikimedia Commons の自由ライセンス作品（CC0 / CC-BY / パブリックドメイン）を使用。

```bash
# 27 ルートの写真をダウンロード（commons.wikimedia.org にアクセスできる通信環境要）
python3 scripts/fetch_photos.py            # 全件
python3 scripts/fetch_photos.py --limit 2  # まず 2 件試す
python3 scripts/fetch_photos.py --dry      # 検索のみ、ダウンロードしない
```

スクリプトの出力：

| ファイル | 役割 |
| --- | --- |
| `public/photos/olle-<番号>.jpg` | 写真（長辺 1600px） |
| `public/photos/manifest.json` | 番号 → 画像のマッピング、起動時に読んで対応ルートへ紐付け（localStorage には書かず、ファイル差し替えで置換） |
| `public/photos/CREDITS.md` | 帰属リスト（作者 / ライセンス / 出典ページ）、CC-BY の帰属要件を満たし、プロジェクトと共に配布 |

スクリプト未実行時はアルバム空、界面は「画像なし」プレースホルダー、エラーにならず。

> 注意：写真は「そのルートの通る場所」の示意写真、**公式ルートの公式撮影ではなく**、**実測軌跡でもない**。ガイドの根拠にするなら公式資料と自身の実写を頼ること。
> 不適切な写真は：`public/photos/` 配下の該当ファイルと `manifest.json` の項目を削除すればよい。

## 7. 出発前準備ページのデータ境界

`/prep` の内容はオルレ公式サイト（jejuolle.org）、韓国観光公社の公開資料、公開旅行記を参考に 2026-09 に整理し、`src/lib/prep.ts` に記述。

- **政策類項目は「出発前再確認」とマーク**（赤小タグ）：ビザ免除の範囲、K-ETA 要否、IDP レンタカー、オルレパスポート価格と緊急電話は変わるため、出発前に再確認。
- **価格は一般的な幅のみ**、予算見積もり用、予約プラットフォームと店舗の最新情報に準拠。
- **具体店名・ホテル名は書かない** — 未確認の名前は作らず、Kakao Maps / Naver Maps で自身で評価を。
- **バス・決済の操作詳細**（T-money カード発行手数料と乗継ぎ、iOS 発行制限、STOP ベルと通過、Uber 対面払い等）は実体験と公開旅行記由来、公式条項ではなく変化が早く、ページ内で赤文字注意と参照リンク付き。
- レンタカー項目は重点注意：韓国は短期滞在者に 1949 ジュネーブ条約紙の IDP を求め、**中国大陸の運転免許は IDP 発給対象外**のため、実務上多くの店が受付けない。自転走には店と書面で事前確認を。
- **女性/男性 よく使うリスト**は「何を持つか、なぜ持つか」の経験的助言、**政策・価格の断言を含まない**；液体容量や保安検査（爪切りは預け荷物推奨）などの硬い規定は `note` に通常枠で注意書きとし、約束としない。両リストの文案は公式 43 項目と意図的に重複させず — さもないと重複排除ロジックに「既にリストにあり」と判定され白書き同然。

### チェックリストのチェック / スキップ状態マシン

`trail100k.checklist`（`src/lib/storage.ts` の `ChecklistState` 参照）は 4 つの相互排他な id 集合を管理：

| 状態 | フィールド | 意味 |
| --- | --- | --- |
| 準備済み | `checked` | チェックした項目、進捗に計上 |
| スキップ済み | `skipped` | 手動スキップ項目、**進捗分母にも未完了にも計上せず**、通常は表示（灰色 +「スキップ」タグ、ワンクリック「復元」） |
| カスタム | `custom` | 自身が追加した項目（`PrepItem[]`） |
| プリセット追加済み | `extras` | 「女性/男性 よく使うリスト」から選んだ項目（`PrepItem` より `from` が 1 つ多い `ChecklistExtra[]`） |

- 項目をチェックすると `skipped` から自動削除（排他）；スキップするとそのチェックを自動解除。
- 「未完了のみ」はチェック済みとスキップ済みを両方隠す；通常モードではスキップ済みも表示し復元しやすく。
- 「グループ全選択」はスキップされていない項目のみに作用、スキップ済みを再チェックしない。
- 進捗バーと各グループの `done/total` は「スキップされていない」項目のみで計算。

### プリセットリスト（女性/男性）のマスターリスト組込み

データ出所は `src/lib/prep.ts` の `PREP_PRESETS`（2 セット独立 id：`preset.f.*` / `preset.m.*`）。
これらは **デフォルトリストではなく**、単なる候補プール：`extras` が空ならページに何も追加されず、ユーザーがいくつか選んだ時だけ「プリセットリスト追加済み」グループが出る。

| 操作 | 挙動 |
| --- | --- |
| 単発「追加」/「削除」 | `extras` の 1 件を書く/消す、トグル同等、再確認なし |
| 「すべて追加（N）」 | `ids` 省略 → 丸ごと統合；ボタン上の N は**重複排除後の実追加件数** |
| 「すべて削除」 | マスターリストから丸ごと削除（Confirm 経由、これら項目のチェック/スキップ状態も連動消去のため） |
| 「リストリセット」 | `checked / skipped / custom / extras` 全消去 |

重複排除基準（`addPresetItems`）：**id で「この件追加済みか」、 `normItemText(text)` で「リストに同じことが既にないか」を判定**（全空白と大小文字を無視）。該当項目は再書き込みせず、セレクターでは「既にリストにあり」と表示してボタン削除。公式グループに同じものが既にある場合も再追加しない — ゆえに両リストの文案は公式 43 項目と意図的重複なし。

⚠️ 重複排除は `setChecklist(prev => ...)` の updater 内で `prev` を基準に計算せねばならず、描画期の `checklist` で判定してはいけない：「追加」を連打すると描画期スナップショットは古く、同じ件を繰り返し書く。同様に、updater が新規なしなら `prev` 元オブジェクトを返し（React は再描画をスキップ、localStorage 書き込みも無駄にしない）。

## 8. エラー時も白紙画面にしない

二層 `ErrorBoundary`（`src/components/ErrorBoundary.tsx`）：

| 層 | 位置 | 捕捉するもの |
| --- | --- | --- |
| 全体 | `main.tsx` が `<App />` を包む | Router / Provider 自身が落ちてもページあり |
| ページ | `App.tsx` 内容部、`key` を pathname に绑定的 | 単ページ崩壊でも上部ナビ残り、別ページに切替て継続可；ルート変更でエラー状態自動リセット |

エラーページ提供：再試行 / ホームへ / エラー情報コピー / コンポーネントスタック展開 / **ローカルデータ消去して再読込**（データに壊れレコードがある時の最終手段、自作 Modal 二段確認）。

⚠️ 捕捉するのは **描画期** エラーのみ。イベントコールバック、`setTimeout`、リクエストコールバック内の非同期エラーは React に上浮かず（「クリックしても反応なし」、白紙にならず）。
`DataProvider` のデータ読込は `requestAnimationFrame` 内で走り、例外も React に上浮かない — そこは別途描画期投擲に変換して境界へ渡し、スケルトン画面での仮死を避ける。

## 9. デプロイ（Docker + nginx + Dokploy サブパス）

プロジェクトは **純静的フロントエンド**（`HashRouter` + `base: './'`）、バックエンドなし、`asset-system-frontend` パラダイムに倣い nginx 静的イメージとしてパッケージ、`/jeju/` サブパス下に配置、Dokploy の Traefik が PathPrefix で振り分け。

### 主要ファイル

| ファイル | 役割 |
| --- | --- |
| `Dockerfile` | 多段ビルド：node 依存インストール + `npm run build`、成果 `dist/` を nginx の `/usr/share/nginx/html/jeju` にコピー |
| `nginx.conf.template` | nginx:alpine 起動時に `templates/*.template` を envsubst で `conf.d/default.conf` に描画；本テンプレートは `/jeju` → `/jeju/` リダイレクト + 静的ホスト + SPA フォールバックのみ |
| `.dockerignore` | node_modules / dist / .git / ローカルスクリプトキャッシュを除外、ビルドコンテキスト縮小 |
| `.npmrc` | npmmirror でコンテナ内 `npm ci` を高速化 |

> `HashRouter` + `base: './'` のため、`dist/` リソースは相対パス、`/jeju/` 下で `vite.config.ts` の変更不要、history ルートの rewrite も不要。

### ローカルでイメージをビルド・自己検証

```bash
docker build -t jeju-100k .
docker run --rm -p 8080:80 jeju-100k
# ブラウザで http://localhost:8080/jeju/ を開き検証
```

### Dokploy へ push

1. Dokploy で **Application** を新規作成、ソースは GitHub 公開リポジトリ `tanabalu/jeju-100k`（main ブランチ）に接続。
2. ビルド方式は **Dockerfile** を選択（多段は既に記述、追加パラメータ不要）。
3. ポート：コンテナは `80` を公開、Dokploy 内ポートは `80` を填入。
4. **Traefik ルート規則**（PathPrefix）：`Path(\`/jeju\`) || PathPrefix(\`/jeju/\`)` を使い、`/jeju` のパス区間だけに一致させます。同一ホストの Pages パス `/jeju-100k/` が Dokploy に取られるのを防ぎます。
5. デプロイ後は `https://your-domain/jeju/` にアクセス（「your-domain」を実際のサブパス宿主ドメインに置換）。

> サブパス変更時は 2 か所：`Dockerfile` の `COPY ... /usr/share/nginx/html/<新パス>` と `nginx.conf.template` 内の `/jeju`、`/jeju/`、`/jeju/index.html`。

## 11. 既知の境界と今後の課題

- 事前登録座標は町レベル近似、**公式軌跡ではない**（ずれは実測で最大 13km、例 `yongsu`、`seogwang`）。
  **実測軌跡のないルートは地図で灰緑破線**（`mapLineSet()` の `approx: true`）—
  破線 = 2 つの近似座標をつないだだけで、歩いた道ではない；軌跡のあるものは実線（白枠 + 緑芯）。
- **24/27 ルートは既に実軌跡あり**（`public/tracks.json`）。まだ欠けているのは **07、14-1、18-2**：
  - `07`(旅行者センター→西帰浦バスターミナル, 12.9km)と `14-1`(저지→서광, 9.3km)は**本島ルート**で信頼できる実測軌跡がまだなく、灰緑破線で表示：
    `07`は2026-07改線後のGPX不足、`14-1`は経路不明(スクリプト`SKIP`除外)。
  - `18-2`(下楸子島)は**離島支線**で、OSM relation / 散way / 全体GPXの三源とも幾何なし、本島地図の視野にも入らず(`chuja` 126.28,33.96)。補うにはWikilocの単体GPXを探すしかない。
  - 離島の `01-1`(牛島)、`18-1`(上楸子島)はOSM海岸路 / 歩道から実幾何を既に補完済み(§1.3参照)。
- **14-1 は明示的に除外**（スクリプトの `SKIP`）：散 way 縫合は 4 セグメントで頭尾ばらばら、GPX セグメントは 189% 超長、
  いずれも不適格 → 示意破線を維持。直すには公式 14-1（저지→서광, 9.3km）の実際の経路をまず確認。
- **2 ルートの距離は依然疑義あり**（幾何自体は信頼できるが公表距離と合わない）：
  `15` 実走 18.67km / 公式 15.5km（120%）；`08` 実走 17.14km / 公式 19.3km（89%）。
  ページは公式値を表示、詳細ページの「軌跡実測」がこの差を露呈。
- **公式宣伝総距離 437km vs ルート別合計 約403km**（`SPECS` 27 ルートの和、フロントエンドの`OLLE_TOTAL_KM`はこれから導出・固定値ではない）—
  この約34kmの差は未解明、公式が「連絡区間」も437に含めた疑い。フロントエンドの距離目標は導出値403を使用、437は「全島」クイックプリセットとしてのみ表示。
- 宿泊 / 見どころ / アルバムは空で事前登録、実際の行程で入力必要（JSON 一括填入も可）。
- 地図背景は OpenStreetMap / OpenTopoMap の無料タイル、通信必要；非通信環境ではオフライン示意図 + 管理者手動座標補正を使用可。
